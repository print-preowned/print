Document reviewed: paystack_escrow_payment_flow_90eebd79.plan.md
Review date: 12 August 2026
Scope: Backend (/Users/naj/Documents/print) and frontend (/Users/naj/Documents/print-web)

Verdict

The plan is structurally sound — separating payment state from fulfillment state, moving stock deduction to payment confirmation, storing webhook events for idempotency, and marking release only on transfer.success are all the right instincts, and they match how the codebase is actually laid out.

But it is not ready to implement. There are four issues that can lose real money or block launch outright, several concrete Paystack API errors that would fail on first contact, and one architectural omission (a ledger) that should be addressed before any money moves.

The single most important thing: the plan treats “Paystack is not licensed escrow” as a marketing copy problem. It isn’t. It’s a flow-of-funds problem that determines the entire architecture, and it should be resolved before Phase 1.

Four blockers

1. Flow of funds and the settlement schedule will break the design as written

The plan holds customer money in the platform’s Paystack balance and transfers out later. Two problems:

  • Legally: a PSSP licence — which is what Paystack holds — explicitly does not authorise holding customer funds. The CBN has been actively fining for exactly this pattern. By collecting on behalf of sellers and disbursing, you are acting as an aggregator holding third-party funds commingled with your operating balance.
  • Operationally: Paystack settles NGN to your bank account on T+1 by default. Your Paystack balance will be near zero when the release job runs, and every transfer will fail on insufficient balance. Nothing in the plan addresses funding the balance or switching to a manual settlement schedule.

Paystack’s own answer to this is Connect / subaccounts with transaction splits, where the seller’s share is settled by Paystack directly to the seller and you never hold their money. With a manual settlement schedule on the subaccount, triggering settlement becomes your escrow release — most of the intended behaviour with dramatically less regulatory and treasury exposure. It costs some control over the exact N-day timing.

Action: Resolve platform-hold vs Connect with Paystack account management before writing migrations. Building platform-hold and discovering later that Paystack won’t approve the flow means throwing away Phases 1, 2, and 4.

2. Deferring stock deduction to charge.success creates paid orders you cannot fulfill

Today _resolve_order_lines checks stock and _create_items deducts it in the same request. Under the new design, two customers can both check out the last copy and both pay; one charge.success webhook arrives and deduct_stock returns False. You have taken money for an order that cannot ship.

The plan must pick a resolution explicitly:

  • Option A: Reserve stock at checkout with a TTL and sweep expired reservations using the same scheduled job.
  • Option B: Accept the oversell and make automatic refund a first-class path in the webhook handler.

Also: _create_items currently raises HTTPException(422) on failed deduction — inside a webhook handler that returns non-2xx to Paystack and triggers retries forever while the order stays stuck.

3. Nothing in the plan prevents paying a seller twice

The escrow status enum is HELD | RELEASE_PENDING | DISPUTED | RELEASED | REFUNDED. There is no in-flight state. If the process crashes between calling Paystack’s transfer API and receiving transfer.success, the row still reads RELEASE_PENDING and the next job run initiates a second transfer.

Compounding this, APScheduler in a FastAPI lifespan runs in every uvicorn worker, so with more than one worker every release fires N times concurrently on day one.

Required together:

  1. A RELEASING / TRANSFER_INITIATED state
  2. Row claiming via conditional update: UPDATE escrow_holds SET status='RELEASING' WHERE id=:id AND status='RELEASE_PENDING' RETURNING id
  3. A deterministic transfer reference derived from escrow_hold.id passed to Paystack’s POST /transfer, so a retry is rejected as a duplicate rather than paying again

4. Chargebacks are absent, and the 7-day window doesn’t cover them

Card chargebacks in Nigeria can land months after the transaction. If you release to the seller on day 7 and a chargeback arrives on day 45, Paystack debits your balance and you have no recourse against the seller.

Paystack emits charge.dispute.create, charge.dispute.remind, and charge.dispute.resolve — none appear in the plan. At minimum, handle those events, and consider a rolling reserve or the ability to withhold future payouts. There’s also no way to claw back after RELEASED — the plan says “handle via support,” which means “absorb the loss.”

Paystack API details that are wrong or missing

These would each fail on first integration:

IssueCorrection
charge.failed does not exist Paystack only sends webhooks for successful transactions. Remove from webhook events table. Detect failure via GET /transaction/verify/{reference} on frontend callback plus a sweep job for stale pending orders.
PAYSTACK_WEBHOOK_SECRET Does not exist. Paystack signs with HMAC-SHA512 of the raw request body using your secret key in x-paystack-signature. Read raw body via await request.body() before JSON parsing; compare with hmac.compare_digest.
gateway_event_id idempotency Paystack webhook bodies are {event, data} with no top-level event ID. Use hash of raw body or composite (event_type, data.id, data.status). Enforce idempotency at state transition with conditional updates, not event dedup alone.
Amounts in kobo Plan never mentions minor units. Codebase uses Numeric(12,2) Decimal; HTTP layer uses float. Need to_minor_units(Decimal) -> int. Webhook must compare verified data.amount and data.currency before marking PAID.
Transfers need OTP disabled Programmatic transfers require disabling OTP on the Paystack account. Dashboard toggle + approval step; belongs in Phase 2 prerequisites alongside enabling Transfers product.
transfer.reversed missing Can arrive days after successful transfer; must move hold back out of RELEASED. Refunds emit pending/processing/processed/failed — plan handles only processed.
Manual admin bank verification Use GET /bank/resolve (Paystack NUBAN resolution). Store resolved name, not seller-typed input.

Economics the model doesn’t capture

  • Paystack fees are nowhere. Card ~1.5% + ₦100 (waived under ₦2,500, capped ₦2,000); transfers ₦10–₦50. At 5% platform fee on ₦10,000 you collect ₦500 and pay ~₦260 in gateway costs.
  • Refunds: Confirm whether processing fee is returned — historically it is not; every full refund is a direct loss.
  • Add gateway_fee_amount column (charge.success includes fees).
  • State rounding policy: platform_fee + seller_net + gateway_fee == gross in minor units.
  • platform_fee_amount and seller_net_amount on both payments and escrow_holds — pick one authoritative source.

Data model corrections

  • payments.order_id unique vs retries: Use partial unique index WHERE status = 'PAID' — retries allowed, double capture impossible.
  • No ledger: Mutable status columns cannot answer “where is this money” after refunds, partial refunds, reversed transfers, disputes. Add append-only ledger_entries (order, direction, amount in minor units, account, reference).
  • PCI/privacy: payment_events.payload stores customer email, IP, card BIN/last4 — needs retention policy; no card data beyond BIN/last4.

Architecture and infrastructure

  • Webhook route: Add to PUBLIC_EXACT_PATHS in app/middleware/auth.py — use exact path, not prefix (prefix would expose all future /webhooks/*).
  • Transaction boundary: get_db commits at request end. Handler must not hold DB transaction open across Paystack verify HTTP call. Pattern: commit raw event first, return 200, process state transition separately and idempotently.
  • httpx not a dependency yet — codebase has no outbound HTTP client. Add in Phase 1 with timeout/retry policy.
  • APScheduler + multi-worker: Job runs per uvicorn worker — needs distributed claiming, not in-process scheduler alone.

Frontend gaps

  • Order detail is a server component (orders/[id]/page.tsx) — “poll until PAID” needs client component + TanStack Query or payment-status island.
  • clearCart() timing: Currently runs immediately after order creation. With PAYMENT_PENDING, customer gets empty cart + unpaid order. Clear only on confirmed payment; add “resume payment” on pending order page.
  • Public key duplication: Response includes publicKey while plan adds NEXT_PUBLIC_PAYSTACK_PUBLIC_KEY. With @paystack/inline-js v2, resumeTransaction(access_code) needs no public key. Inline keeps PCI SAQ-A.

Sequencing

  • Phase 2 hard-blocks checkout on active payout account, but Phase 3 is frontend checkout — shipping Phase 2 first kills checkout for all sellers with no payout account. Gate behind flag or move last.
  • Removing customer POST /orders must not happen until frontend migrates.
  • Gate placement inconsistent — block at publish (listing) not checkout for better UX.
  • Reconciliation in Phase 6 is too late — need daily Paystack vs payments comparison from day one of real money.

Smaller inconsistencies

  • State diagram: HELD → RELEASE_PENDING vs DELIVERED → RELEASE_PENDING: escrow_job — pin to synchronous status transition on PATCH.
  • No expiry for PAYMENT_PENDING orders — same scheduler needs abandoned-checkout sweep.
  • Gateway-neutral naming: adding provider varchar default 'paystack' now is cheap; /webhooks/paystack route name is fine.

Test plan additions

  • Signature verification rejects tampered body
  • Verified amount mismatch refuses PAID
  • Retried transfer with same reference does not double-pay
  • Two concurrent release job instances → exactly one transfer
  • transfer.reversed correctly un-releases
  • charge.success with no stock triggers refund, not 422 retry loop

Recommended next steps (before writing code)

  1. Resolve flow-of-funds with Paystack: platform-hold vs Connect subaccounts with manual settlement
  2. Decide stock reservation strategy (TTL reserve vs auto-refund on oversell)
  3. Add ledger to data model
  4. Add double-payout prevention (RELEASING state + conditional claim + deterministic transfer reference)
  5. Fix Paystack integration specifics (no charge.failed, secret-key signing, kobo amounts, transfer.reversed, dispute webhooks)
